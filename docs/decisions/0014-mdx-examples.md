# 0014: MDX examples and section pages

- **Date:** 2026-09-07
- **Status:** accepted

## Context

Examples and section pages are Markdown. `chunkify()` (`src/loaders/utils/chunkify.ts`) runs remark over a `.md` file, turns every fenced block in a playground language into a `{type: 'code'}` chunk and everything else into `{type: 'markdown'}` chunks, and `generateExamplesModule()` (`src/vite/modules/examples.ts`) emits a virtual module whose default export is that array, with an `evalInContext()` bound to a statically built `require()` map on each code chunk. The browser renders the array in `Examples.tsx`: code chunks become playgrounds, Markdown chunks go through markdown-to-jsx with the override map in `Markdown.tsx`.

The limit of that design is that prose and components cannot mix. A documentation page cannot use a callout, a tabbed comparison, a props matrix or any other component of the design system it documents; it can only put components inside a playground, where they are editable source code rather than page furniture. MDX is the ecosystem's answer, every comparable tool (Storybook, Docusaurus, Nextra) has it, and it is the most frequently requested feature inherited from upstream ([0007](0007-backlog-adoption.md)).

Three constraints shape any answer. First, **nothing may change for a style guide without an `.mdx` file** — the `.md` pipeline, its URLs, its `docs.json` output and its dependency footprint stay exactly as they are. Second, **the playground contract is not negotiable**: a playground is a source string that the browser compiles with sucrase and runs through `evalInContext` + `requireInRuntime`, whose map is built by a static scan of the fences (`getImports.ts`); `updateExample`, the fence modifiers, `exampleMode`, `usageMode`, the `Editor` slot and the isolated-example URLs all hang off that. Third, `@mdx-js/mdx` is a large dependency for a feature most users will not use: measured against the packages already in this repo's tree, it adds **57 packages and 1.87 MB**, and with `remark-gfm` **73 packages and 2.38 MB**. The `unified` 11 / `remark-parse` / `micromark` / `vfile` / `acorn` half of its tree is already here for `remark` and `getAst`.

A spike (Vite 8.2.2, React 19, `@mdx-js/mdx` 3.1.1) established the mechanics: `compile()` with `{jsx: true, outputFormat: 'program'}` produces a `MDXContent` component with JSX intact; a remark plugin can replace playground fences with `<RsgPlayground index={n}/>` while collecting `{content, lang, settings}` in the shape `chunkify()` already produces; the component map can be supplied at render time through the `components` prop with no `providerImportSource`; a virtual module that `addWatchFile()`s the `.mdx` hot-reloads; and a compile error surfaces in Vite's dev overlay and fails `vite build`. It also found that `@vitejs/plugin-react` 6 will **not** transform the module (its filter is `/\.[tj]sx?$/` over the id, and ours is `\0rsg-mdx:…`), so the JSX has to be lowered with `transformWithOxc()` — the call `src/vite/jsxInJs.ts` already makes — and that MDX rejects six pieces of syntax Markdown accepts, of which indented code blocks are the dangerous one: an indented `<Button/>` becomes a live component instead of a playground.

## Options considered

1. **A parallel MDX pipeline behind an optional peer dependency (chosen).** A new `rsg-mdx:` virtual module next to `rsg-examples:`, a remark plugin that reproduces `parseExample()`'s fence handling and hands the collected code to the existing codegen, a new `MdxPage` client component, and `@mdx-js/mdx` declared in `peerDependenciesMeta` as optional and imported lazily the first time an `.mdx` file is discovered. No `.md` code path changes; users who never write `.mdx` install nothing.
2. **Replace the Markdown pipeline with MDX.** One parser, one renderer, no drift, and markdown-to-jsx (with its Preact `reviveElements` workaround in `Markdown.tsx`) could be dropped. Rejected: it makes a 1.87 MB dependency mandatory, and MDX is not a superset of Markdown — indented code blocks, `<!-- -->`, `<br>`, autolinks and GFM all behave differently, so every existing `Readme.md` in the wild becomes a potential compile error. That is a 2.0, not a beta.
3. **`.mdx` as a `.md` superset via a custom micromark extension.** Keep CommonMark semantics and add only JSX. Rejected: it is a parser project, not a feature, and the result would not be MDX — user remark plugins, editor tooling and the mental model would all disagree with it.
4. **Support MDX only for section content pages, not component examples.** Halves the client work (no `Examples.tsx` branch, no isolation changes). Rejected: component pages are where prose and components most want to mix, and the two discovery paths already share `examplesId()`, so the saving is small.
5. **`@mdx-js/mdx` as a regular dependency.** Simpler resolution, no missing-dependency error paths. Rejected on footprint: 57 packages for a feature most style guides will not use, in a package that is otherwise careful about its install size.
6. **Compile MDX to `_jsx()` calls (`jsx: false`) instead of lowering JSX ourselves.** Fewer moving parts. Rejected in favour of `jsx: true` + `transformWithOxc()`, which keeps the JSX runtime, dev/production flag and import source in one place next to `jsxInJs.ts` and gives one transform to blame when output differs from the rest of the client.

## Decision

Option 1, shipped in 1.0 while the `next` channel is still open ([0003](0003-versioning-and-release-channels.md)), with this contract:

1. **Discovery, on by default.** The default `getExampleFilename` candidate list becomes `Readme.md`, `Readme.mdx`, `<Component>.md`, `<Component>.mdx`, `<Folder>.md`, `<Folder>.mdx` — interleaved by base name, so `.md` wins over `.mdx` for the same base name and the existing “Readme beats ComponentName beats FolderName” precedence is untouched. `sections[].content` and the `@example` doclet accept `.mdx` by extension. `getExampleFilename` keeps its signature: **the extension of the path it returns selects the pipeline**, which is what makes a custom implementation work with MDX without a new option. There is no `mdx: false` switch: a style guide with no `.mdx` file is unaffected, and one with an `.mdx` file wants it rendered.
2. **The virtual module.** `rsg-mdx:<file>?displayName=&component=&default=1`, resolved and loaded like `rsg-examples:`, exporting `default [{ type: 'mdx', Content, examples }]` — an array of one chunk, so `Array.isArray(content)`, `examples.length > 0`, `filterComponentsWithExample()` and `getAllContentPages()` keep working unchanged. Every entry of the inner `examples` array is exactly today's `RuntimeCodeExample`, produced by the existing `getImports` → `requireMap` → `evalInContext` codegen, so `Playground`, `Preview`, `compileCode`, the require shim, `updateExample`, the fence modifiers, `exampleMode`, `usageMode` and the `Editor` slot need no changes.
3. **Index numbering: `.md` keeps counting prose, `.mdx` counts playgrounds.** For an MDX page, `index` is the ordinal of the playground on the page — there is no equivalent of a prose chunk. `#!/Button/1` isolates the second playground, `filterComponentExamples()` and `filterSectionExamples()` return `[chunk.examples[index]]` (a plain code chunk the existing renderer handles), and `docs.json`'s `ManifestExample.index` uses the same ordinal so the manifest and the URLs still agree. Renumbering the `.md` path to match was considered and rejected: it would change every existing `#!/Button/2` URL and the `index` field of `docs.json` for a cosmetic gain. The difference is documented in `Documenting.md`, not reconciled.
4. **Static fences keep build-time Prism.** MDX has no raw-HTML passthrough, so a non-playground fence is replaced with `<RsgStatic lang html/>` carrying the `highlightCode()` output, rendered through the existing `Pre`/`Code` renderers. Prism stays out of the browser bundle and `styles.Pre` keeps applying.
5. **The component map is the Markdown one, plus `mdxComponents`.** The overrides in `Markdown.tsx` are extracted into a shared `markdownRenderers` object consumed by both paths, so `styleguideComponents` and `styles` apply identically to Markdown and MDX prose. `mdxComponents` is a **flat map merged over that element map** — one level, no `(defaults) => map` callback — so a lowercase key replaces an HTML element renderer and a capitalised key adds a shortcode every `.mdx` page can use without importing it. `mdx: { remarkPlugins, rehypePlugins, recmaPlugins }` passes plugins to `compile()`, and those lists are typed as `readonly unknown[]` in the published `.d.ts`: a stronger type would mean the shipped declarations reference `unified`, forcing consumers to install it. The cast happens once, at the `compile()` call site.
6. **GFM is on by default.** `remarkPlugins` defaults to `[remarkGfm]`. Tables are the first thing anyone writes in component documentation and the `.md` path renders them today (markdown-to-jsx does GFM), so shipping without it would make “my table renders as a paragraph” the first bug report from every MDX user. Setting `mdx.remarkPlugins` replaces the default list, which is the escape hatch for anyone who wants plain CommonMark.
7. **`@mdx-js/mdx` and `remark-gfm` are optional peer dependencies** (`peerDependenciesMeta.optional`) and devDependencies of this repository, so the tests and the type-check see them while consumers install them themselves. They are resolved lazily, on the first `.mdx` file, with `createRequire(config.configDir)` first and our own tree as the fallback — the trick `getReactRootFlavor()` already uses, and what makes an optional peer resolvable under a strict pnpm layout. Missing: an `.mdx` found by _discovery_ logs a warning naming the file and the install command and is skipped, so an unrelated `Readme.mdx` never breaks an existing build; an `.mdx` named _explicitly_ (`sections[].content`, `@example`, a custom `getExampleFilename`) throws a `StyleguidistError` naming the package to install, because the user asked for that file by name.
8. **`docs.json` and `llms-full.txt` get extracted prose, not raw MDX.** A second pass over the same MDAST serialises non-code nodes back to Markdown; JSX elements and expressions are kept as their MDX source, `import`/`export` statements are dropped, playgrounds are written back as fences. `ManifestComponent` and `ManifestSection` gain an additive `format: 'md' | 'mdx'`; `MANIFEST_SCHEMA_VERSION` stays `1`. `parseMdx()` is asynchronous, so **`buildManifest()` and the dev-server middleware that calls it become `async`** rather than driving the compile through a synchronous barrier: both call sites already tolerate a promise.
9. **HMR is the `.md` mechanism.** `load()` calls `addWatchFile()`, `hotUpdate` invalidates the module, and the create/delete branch that today keys on `.md` accepts `.mdx` so a newly added `Readme.mdx` re-runs discovery for the affected components.
10. **React 16.14 stays the floor.** The compiled MDX uses the automatic JSX runtime, which is what the client is already compiled with ([0013](0013-react-16-support.md)); the lowering happens through `transformWithOxc()` with the same options as `jsxInJs.ts`, so Preact's `react/jsx-runtime` alias covers MDX too.
11. **Out of scope for 1.0:** playground code reading the page's ESM imports (the require map is built from a static scan of the fences; page-level imports are supported, playground scope is not), named MDX exports being visible outside the page, custom MDX layouts (`export default`), and YAML frontmatter. All of them stay reachable through `mdx.remarkPlugins`.

## Consequences

- Users who never write `.mdx` get a byte-identical style guide and install nothing new. Users who do add two dev dependencies and 73 transitive packages.
- MDX is not a Markdown superset, and the differences will generate support traffic: indented code blocks become live JSX rather than playgrounds, `<!-- -->` and non-self-closing void elements and angle-bracket autolinks are compile errors, and a curly brace in prose starts an expression. Documenting.md gets a prominent box listing all six, indented blocks first — Documenting.md's own examples are written with indented blocks.
- Two isolate-URL numbering schemes exist side by side (`.md` counts prose chunks, `.mdx` counts playgrounds). Aligning them stays possible only while the `next` channel is open ([0003](0003-versioning-and-release-channels.md)); by deciding against it here, aligning them later becomes a breaking change and needs its own record.
- Enabling GFM by default means `remark-gfm` is a second optional peer dependency, and a user who sets `mdx.remarkPlugins` silently loses tables unless they list it again. The option's documentation says so.
- `buildManifest()` in `src/vite/machineReadable.ts` changes signature, which is a break for anyone calling it directly. It is not part of the documented Node.js API ([API.md](../API.md)), and the change lands during the beta.
- Prose now has two renderers. The shared `markdownRenderers` object keeps the component map from drifting, but a `styleguideComponents` override has to look right under both markdown-to-jsx and MDX, and edge cases (raw HTML, comments, GFM) will differ.
- MDX output is produced by real `jsx()` calls, so it does not need the `reviveElements()` workaround markdown-to-jsx forces on Preact.
- A ninth example style guide (`examples/mdx`) joins the CI matrix and the published examples on the docs site, and `test/e2e/examples.spec.ts` walks it for free.
- Option 2 (MDX everywhere, markdown-to-jsx removed) stays open for 2.0 and would need its own record, including a migration story for `.md` files that MDX rejects.
