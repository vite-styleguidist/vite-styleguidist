# 0016: “On this page” navigation (`pageNav`)

- **Date:** 2026-09-07
- **Status:** accepted

## Context

A per-page list of the current page’s headings — the rail most documentation sites have — was requested as an opt-in, backward-compatible feature. Three constraints shape it.

The name is taken: `TableOfContents` is the sidebar, and that name appears in the public `styles.TableOfContents.*` keys, in `styleguideComponents.TableOfContentsRenderer` and in the `tocMode` option, none of which can be renamed under [0011](0011-facelift-and-dark-mode-contract.md).

The two prose pipelines are not symmetric. `.md` headings already carry ids: verified, `markdown-to-jsx@9.10.2` slugifies them and passes `id` through the shared override map to `MarkdownHeading` (`## Some Heading, with punctuation!` → `some-heading-with-punctuation`, with `-1` de-duplication _within one `compiler()` call_ — two `<Markdown>` blocks on one page can therefore emit the same id). `.mdx` headings carried **no id at all**: verified, the compiled page was `<_components.h2>{"Usage & setup"}</_components.h2>`, so `#some-heading` deep links silently did nothing on MDX pages. That is fixed separately, in the remark pass `src/loaders/utils/mdx.ts` already runs, and it ships whether or not `pageNav` is enabled.

The layout has no free column: `sidebarWidth` 232 plus the 960 px content column (plus its two `space[6]` page gutters) plus a rail and its gutter is more than 1440 px, and the 960 px column is the approved artboard width.

## Options considered

1. **Build-time headings in `docs.json` and the virtual module.** Free for MDX, and the shape an MCP server would want. Rejected for v1: for `.md` the ids are generated by markdown-to-jsx at render time, so a build-time list is only correct if the client is also handed the same `slugify`; and it changes the manifest, which has its own schema version.
2. **Collect headings from the rendered page.** Pipeline agnostic, correct by construction, correct even when `styleguideComponents` replaces the heading renderer, and it touches neither the loader nor `docs.json`. Chosen.
3. **A second sidebar section** listing the current page’s headings inside the existing `TableOfContents`. Rejected: it changes a component people override and mixes two navigation axes in one list.
4. **Reuse the sidebar’s scroll-spy or build a second one.** Reuse: 0015’s `useScrollSpy` is exactly the same mechanism at heading granularity.
5. **Show the rail only above the breakpoint, or change its shape below it.** Change its shape: a feature that only exists above 1480 px would be invisible on the laptops most readers use.

## Decision

Add an opt-in `pageNav` feature, named `PageNav` in code (`PageNav` + `PageNavRenderer`), labelled “On this page” in the UI.

1. **Config option** `pageNav`, `false` by default, `true` to enable. The schema accepts `['boolean', 'object']` and its `process()` rejects an object with a message saying the per-page options are not implemented: the object form (`{ minLevel, maxLevel, title }`) is where the option is meant to grow, and refusing it now is what makes adding it later non-breaking — nobody can have a config in the wild that silently means something else. The client only ever asks whether the value is truthy. `'pageNav'` is in `CLIENT_CONFIG_OPTIONS`.
2. **Headings come from the rendered page**: `h2[id], h3[id]` inside `#rsg-content`, in document order, first occurrence of a duplicate id, skipping anything inside a preview or a code editor (a heading an example renders is content, not structure). Re-collected when the route changes and, debounced by 100 ms, whenever the content mutates (`MutationObserver`), so lazily loaded MDX pages and expanded examples are picked up. PageNav renders inside the element it observes, so an unchanged list is dropped rather than written back to state; that is what ends the loop.
3. **The list renders only where it helps**: on pages that show a single component or section — every `pagePerSection` page (whose `displayMode` stays `all`, so the flag is checked first), the `#/Section` routes, and the isolated `#!/Name` views. Not on the default all-in-one page, where the sidebar is the page navigation and already follows the scroll (0015), and not on `notFound`. Nothing renders on a page with fewer than two headings. The narrower variant this leaves open — the current component’s headings in the default mode — is additive: it relaxes one function and passes PageNav another root.
4. **Two shapes, one component.** From a new `theme.mq.large` up, a sticky rail beside the content column; below it, the same list as a native `details`/`summary` block above the content, closed by default. Which one is rendered is decided in JavaScript (`useMediaQuery`), not by hiding a second copy, so there is one landmark, one set of links and one tab stop per entry at every width.
5. **The breakpoint is computed from the tokens**: `sidebarWidth` 232 + the content column 1056 (960 + 2 × `space[6]`) + the rail’s gutter `space[3]` 24 + `pageNavWidth` 168 = **1480 px**. The rail is 168 px rather than the 220 px the study sketched because 220 would put the breakpoint at 1532 px, above every 1440 and 1512 px laptop. The content column never narrows: `<main>` becomes a centred two-track grid whose first track is capped at 960 px, and the rail’s track is `auto`, so a page with nothing to list leaves the column exactly where a style guide without the option puts it (measured: the same x on both).
6. **The highlight is [0015](0015-scroll-synced-selection.md)’s `useScrollSpy`**, applied to heading ids instead of component slugs. The rail never writes the URL.
7. **Links reuse the existing in-page mechanism.** On a routed page the fragment _is_ the route, so an entry links to `#/Route?id=heading`, the `?id=` parameter `src/client/index.ts` already scrolls to, subtracting `--rsg-sticky-offset`; elsewhere a plain `#heading`. PageNav adds no scrolling and no motion of its own, so there is nothing for `prefers-reduced-motion` to opt out of. That mechanism was a `hashchange` listener alone, which a cold load never fires and a repeat click on the same entry cannot produce: opening one of these links in a new tab landed at the top of the page, and clicking the entry the reader was already on did nothing at all. PageNav therefore re-dispatches `hashchange` from a click that would not change the address — the handler it passes the renderer as `onHeadingClick` — which hands the repeat click to exactly the same code as the first one. `index.ts` now also runs it once after the first render, retrying for a few frames while the target is still being committed, and only when the fragment names an element — the “otherwise scroll to the top” half would fight the browser’s scroll restoration on every routed page.
8. **New public surface, all additive**: `styleguideComponents.PageNav` / `PageNavRenderer` (props `{ headings: { id, text, level, href }[], activeId, title, collapsible, onHeadingClick }`), the `styles` key `PageNav` with the rules `root`, `title`, `list`, `item`, `link`, `isSelected`, `isChild`, `isCollapsible`, `details` and `summary`, the theme keys `mq.large` and `pageNavWidth`, a `pageNav` prop on `StyleGuideRenderer`, the new rules `hasPageNav`, `contentColumn` and `pageNav` under `StyleGuide`, and the testids `rsg-pagenav`, `rsg-pagenav-link` and `rsg-pagenav-summary` inside a `<nav aria-label="On this page">` whose current entry carries `aria-current="location"`. Colours are only the pairs the contrast guard already covers (`light`, `base` and `link` on `baseBackground`, `base` on `selectedBackground`), so both schemes are AA without a new token.

## Consequences

- Default-off means no existing style guide changes in any way until its author opts in; a later decision could flip the default, and would be reversible only at a major.
- `.md` pages can contain duplicate heading ids (two component descriptions with `## Usage`). The rail lists the first occurrence, so some entries can point at the wrong heading until page-scoped slugging is fixed separately.
- Users who replaced `StyleGuideRenderer` must render the `pageNav` prop themselves, the same rule that already applies to `toc`; without that the option appears to do nothing for them, and the docs say so. The `examples/customised` style guide is exactly that case, and it is also in the default display mode, so it is deliberately left off there.
- The list is in the DOM before the content in both shapes. That is the reading order of the collapsible block; for the rail it means the entries come before the content in the tab order although they are drawn to its right. Accepted: it is a navigation landmark, the sidebar sits in front of the content for the same reason, and the alternative (moving the node when the breakpoint is crossed) re-mounts the component on every resize across it.
- Because the highlight is 0015’s, its bottom rule applies here too: once the document is scrolled to its bottom the last entry is current, even though the headings above it are still on screen. The rule is what makes a short final section reachable at all, and heading-level navigation makes it visible more often than component-level navigation did. _Clicking_ an entry in that last screenful is not affected: 0015’s pin holds the clicked entry until the reader scrolls, and `readHashId` recognises the `?id=` fragment these links use as well as a plain `#slug` — which is what makes the pin reach this consumer at all.
- Anything the style guide renders without a class of its own inherits the surrounding page’s CSS: the `details` element needs a rule purely so that the jss-plugin-isolate reset stands in front of it. The sections example, which paints every bare tag magenta, is what catches that.
- Build-time headings (for `docs.json`, `llms.txt` and the planned MCP server) stay open and need their own record, including whether `MANIFEST_SCHEMA_VERSION` moves; the loader-side collection is ~43 bytes per heading and costs no measurable time.
- Out of scope and named as such: h4–h6, numbering, “back to top”, per-section configuration, a rail in the default display mode, heading anchor-link affordances, and collecting headings from anything but the rendered page.
