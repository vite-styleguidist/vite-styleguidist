# 0012: AI integration

- **Date:** 2026-09-06
- **Status:** accepted

## Context

A style guide is documentation, and documentation is increasingly read by AI coding assistants rather than (or before) people: an assistant asked to “add a `Button` like the ones in our design system” does better when it can read the design system’s own props tables and examples instead of guessing from the source code. A React Styleguidist build is a single-page app that renders its content from a JavaScript bundle, which is the worst possible shape for that: a fetcher sees an empty `<div id="rsg-root">`. The information exists, though. The Vite plugin already parses every component with react-docgen and every Markdown file with remark to build the virtual modules the browser gets, so nothing new has to be parsed; it only has to be written down in a second format.

Two conventions have emerged for that: [llms.txt](https://llmstxt.org/) (a Markdown index a site serves at `/llms.txt`, optionally with an `llms-full.txt` holding everything) for assistants that fetch documentation, and the [Model Context Protocol](https://modelcontextprotocol.io/) for assistants that call tools. The 1.0 line is the moment to decide what the project ships, because whatever it emits becomes a format users’ tooling depends on.

## Options considered

1. **Emit `docs.json`, `llms.txt` and `llms-full.txt` from the build**, generated by the same functions that produce the virtual modules; serve them from the dev server too. No new dependencies, no runtime, works with every host that can serve static files.
2. **Ship an MCP server only.** The most capable integration (search, per-component queries, live data), but it needs a process running next to the assistant, and every user has to configure it; a static site gains nothing.
3. **Both, in two steps:** the files in 1.0, an MCP server that reads `docs.json` in 1.1.
4. **Nothing.** Leave it to users to scrape the built HTML or write their own extractor against `updateDocs`. Several would, each differently.
5. **Where the files come from:** a second, independent extractor (simpler to write) versus the same code path as the virtual modules. A second parser drifts: a `@visibleName`, an `updateDocs` hook, a `skipComponentsWithoutExample` filter that one applies and the other forgets is a bug report waiting to happen.

## Decision

**Option 3, built the way option 5 prescribes.** Version 1.0 emits three files next to `index.html` on every `styleguidist build` and serves them from the dev server (regenerated per request, with the react-docgen work memoized on file mtimes), controlled by the `machineReadable` config option, on by default:

- `docs.json`: the manifest. Sections in sidebar order, each with its components; a component carries its name, `@visibleName`, slug and relative link, its file path relative to the project, description, JSDoc tags, props (with the type printed as the props table prints it: `string`, `oneOf: small | normal | large`, `func`, or the TypeScript annotation as written), public methods, and usage examples with the prose that precedes each one. It carries a `schemaVersion`, bumped only on incompatible changes; adding fields is not one.
- `llms.txt`: the llmstxt.org index, one link per component, relative to the style guide.
- `llms-full.txt`: the whole guide as one Markdown document, props as tables, examples as fenced code.

They are built by `buildManifest()` in `src/vite/machineReadable.ts` from `collectSections()`, `generatePropsModule()` and `parseExamples()`, the functions the virtual modules use, so the files can’t say something the style guide doesn’t. Links are relative because a build doesn’t know where it will be deployed; a URL option can be added later without a schema change.

**Future (1.1, not part of this decision’s implementation):** an MCP server, published as a separate package or a `styleguidist mcp` command, that reads `docs.json` (from a build directory or a deployed URL) and exposes tools to list components, get one component’s props and examples, and search descriptions. It will read the manifest rather than parse sources, so it works against a deployed guide as well as a local one, and so that the file format is the single contract between the two. Its design is a new record when the time comes; this record only commits to `docs.json` being that contract.

## Consequences

- Every deployed style guide exposes its documentation as plain text. That is the point, but it is also new: the option is documented with a warning, and `machineReadable: false` turns it off. Nothing in the files is secret that the rendered page doesn’t show, but the page needs a browser and the files don’t.
- The `docs.json` shape is public API from 1.0 on. Incompatible changes bump `schemaVersion` and are breaking changes of the package; additive changes aren’t.
- The Node side now depends on two more of its own modules being pure: `getUrl()` (the client’s link builder, reused so that links match the sidebar) and the parsing helpers. Tests pin the output for the fixture components, nested sections and `pagePerSection` links.
- Highlighted code is un-highlighted for the manifest (the loaders bake Prism markup into descriptions and prose). Should the loaders ever stop highlighting on the Node side, that step becomes a no-op rather than a bug.
- The MCP server has a data source it can rely on before it exists; the sooner `docs.json` is in real use, the sooner its shape is vetted by something other than its own tests.
